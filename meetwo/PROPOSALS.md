# meetwo 追加実装案

現状(`SPEC.md`参照)からの追加実装候補をまとめる。すでに実装済みの `/list` バグ修正・サーバー設定のVec化・`/status`・`/stop`(権限制限なし)は含まない。

## 1. RCONコマンドの汎用化(`/rcon` コマンド)

> `/stop`は個別コマンドとして実装済み(権限制限なし)。以下は任意コマンドを実行できる汎用版の案。

- **内容**: `rcon::run` は既に任意のコマンド文字列を実行できる汎用関数になっているので、これをDiscordから直接叩ける管理者限定コマンドを追加する。
  ```
  /rcon server:<name> command:<任意のMinecraftコマンド>
  ```
- **想定用途**: `/tp`, `/give`, `/weather clear`, `/whitelist add` など、say/list以外の運用作業をDiscordから行えるようにする。
- **注意点**:
  - 誰でも実行できると危険なので、`poise`の `#[poise::command(..., required_permissions = "ADMINISTRATOR")]` やロールチェックで実行者を制限する。
  - 実行ログ(誰が・いつ・何を打ったか)を別途記録しておくと事故時に追跡できる。
- **優先度**: 中(利便性は高いが権限制御を誤ると事故につながるため慎重に)

## 2. ログイベント種別の拡充

- **内容**: 現在監視している正規表現(chat, join/leave, death, advancement, start, stop, rcon)に加えて以下を追加。
  - サーバークラッシュ検知: ログファイルが一定時間(例: 5分)更新されない場合に警告を送る
  - TPS/ラグ警告ログ(`Can't keep up!` 等)の検知
  - バックアップ完了ログの検知(バックアッププラグインを使っている場合)
  - 天候変化(`re_weather` 的なパターン)
- **実装イメージ**: `main.rs` の `patterns: LogPatterns` に正規表現とフォーマッタを追加するだけで良い(既存の仕組みに乗るため実装コストは低い)。クラッシュ検知だけは「一定時間ログが増えない」を見る別ロジック(`write_discord`ループ内でファイル更新時刻を比較)が必要。
- **優先度**: 低〜中(運用しながら必要なものを都度足していく形で十分)

## 3. バーストメッセージの間引き・まとめ送信

- **内容**: 現在は1ポーリング(1秒)内でマッチした行ごとに`channel_id.say`を個別に呼んでいる。join祭りやチャット連投などで短時間に大量のログが出た場合、Discordのレート制限(chat message rate limit)に引っかかる可能性がある。
- **実装イメージ**: `write_discord`内で1ポーリングぶんのマッチ結果を`Vec<String>`にため、`\n`区切りで結合してから1〜数回のメッセージ送信にまとめる(Discordの1メッセージ2000文字制限を考慮して分割送信するロジックも必要)。
- **優先度**: 低(現状のアクセス規模で頻発する問題ではなさそうだが、サーバー再起動直後の大量join等では発生し得る)

## 4. ログ監視をポーリングからイベント駆動に変更

- **内容**: 現状1秒間隔でファイルサイズをチェックするポーリング方式。`notify`クレート(inotify/kqueue等のラッパー)を使えばファイル変更イベントを直接受け取れる。
- **メリット**: 反応速度の向上、無駄なsleepループの削減。
- **デメリット/検討事項**: Dockerでホストのログディレクトリをbind mountしている場合、mountの種類(overlay等)によってはinotifyイベントが正しく飛ばないことがあるため、導入前に動作検証が必要。
- **優先度**: 低(現状1秒ポーリングで実用上困っていなければ後回しでよい)

## 5. RCON接続の使い回し(mcrconプロセス起動オーバーヘッドの削減)

- **内容**: 現在は`/list`・`/status`・チャット中継のたびに`mcrcon`プロセスを都度起動している(プロセス起動コスト + TCP接続の張り直し)。呼び出し頻度が上がると無視できないオーバーヘッドになる。
- **実装イメージ**: `mcrcon`外部コマンドへの依存をやめ、RCONプロトコルをRustで直接実装する(または`rcon`クレート等の既存ライブラリを利用)。サーバーごとにコネクションを張りっぱなしにして再利用する。
- **注意点**: 接続が切れた場合の再接続処理が必要になる。実装コストは他の案より高め。
- **優先度**: 低(チャット中継の頻度がそこまで高くなければ現状の都度起動でも実用上問題ない)

## 6. `/status` の表示強化

- **内容**: 現状は`list`コマンドの生出力をそのまま貼り付けているだけ。以下のような整形を検討。
  - オンライン人数だけを抽出して見やすく表示(例: `🟢 server1: 起動中 (3/20人)`)
  - Embed形式にしてサーバーごとに色分け・アイコン表示
  - 最終ログ更新時刻を合わせて表示(ログが止まっていれば「クラッシュしている可能性」を示す)
- **優先度**: 低(見た目の改善なので後回しでよい)

## 優先度まとめ

| 案 | 優先度 | 理由 |
|---|---|---|
| 1. `/rcon` 管理者コマンド | 中 | 運用上の利便性が高い。権限制御の設計が必要 |
| 2. ログイベント拡充 | 低〜中 | 必要になったタイミングで都度追加できる |
| 3. バーストメッセージ間引き | 低 | 発生頻度が低ければ緊急性はない |
| 4. ポーリング→イベント駆動 | 低 | 現状の1秒ポーリングで実用上問題ないなら後回し |
| 5. RCON接続の使い回し | 低 | 呼び出し頻度が低い間は都度起動で十分 |
| 6. `/status` 表示強化 | 低 | 見た目の改善 |
